# 电脑摄像头与香橙派硬件网关方案

> **历史方案，分工已更新：** 香橙派不再作为主链路硬件网关，改为旁路边缘分析节点。以 [电脑主流程与香橙派旁路分析计划](pc-main-orange-pi-sidecar-2026-11-17.md) 为准。下文保留历史决定与代码分析供追溯，不作为 USB 移接或网关实施指令。

更新：2026-11-17。本文记录分工决定和实施计划，不代表相关功能已经实现或通过实机验收。

## 已确认决定

- 摄像头数据直接接入电脑，不经香橙派。用户照片显示 ESP32-CAM、排线标注 OV3660，拟通过 Wi-Fi 视频流接入，不能按普通 USB/UVC 摄像头处理；固件和性能仍需实测。
- 香橙派作为硬件网关，连接 Arduino，转发状态、控制命令和执行回执。
- Arduino 保留传感器采集、自动控制、密码键盘、舵机和 OLED 等本地功能。
- 电脑负责网页、Flask 业务后端、数据库及视觉识别。视频预览与识别分离是下一阶段改造方向。

## 目标链路

```text
ESP32-CAM -> Wi-Fi / JPEG 视频流 -> 电脑单路接收与分发 -> 浏览器实时预览
                       -> 最新帧抽样 -> 独立视觉识别 -> Flask/数据库 -> 网页结果

网页 -> Flask -> 香橙派网关 -> Arduino -> 执行器
网页 <- Flask <- 香橙派网关 <- Arduino 状态/事件/执行回执
```

针对 ESP32-CAM，第一阶段先验证 JPEG/MJPEG 流和电脑单路接收，独立于识别做预览。WebRTC 为后续可选分发方式；MediaMTX 不能被假定可直接接收该 HTTP MJPEG 输入，需要兼容的桥接/转码程序并测量额外延迟，尚未部署。第一阶段用独立预览页验证，之后替换现有 GUI 的 YOLO 图片轮询预览。识别截图与实时视频分别展示，避免旧检测框错配新画面。

Flask 继续处理业务接口；推理与视频分开运行。数据库先保留 SQLite。暂不因视频流畅度目标而迁移后端框架，也不把完整视频默认逐帧入库。

## 网关与 Arduino 通信：实施前必须确认

优先评估 USB 串口，但尚不能按现有接线直接启用：键盘占用了 D0/D1。如果板卡是 UNO R3，这两脚与 USB 串口使用的 RX/TX 共用，必须先调整接线/扩展键盘引脚，或根据板型选择独立可用串口。A4/A5 也已经用于键盘，不能假定 I²C 空闲；不能直接把软件串口当成已验证替代方案。

两块板均为 UNO R3（用户确认）。需硬件组提供：与代码对应的完整接线表、扩展板与摄像头供电底板信息。两板分工已可从源码初步确定，摄像头尚未配置。另一块板已有脉冲协议，不能未经确认替换为网关线路。

参考：[Arduino UNO Rev3 官方说明](https://store.arduino.cc/products/arduino-uno-rev3/documentation/)，[UNO R3 引脚图](https://content.arduino.cc/assets/A000066-full-pinout.pdf)。具体电气连接按实际板卡文档核实；不要直接连接未经核实电平的 GPIO。

## 拟定通信约定（待硬件组共同确认）

- 建议使用有长度限制、换行分帧的简单消息。具体 JSON Lines 或紧凑文本格式依据 MCU 内存确定，不先引入大型解析依赖。
- 状态至少含：启动标识、递增序号、运行时间、温湿度及有效性、明暗、风扇/灯模式和开关、舵机目标状态、雨水/土壤 known 和 wet。
- 命令含唯一 ID、目标、动作、参数和有效期。第一版仅支持当前真实能力：风扇/灯的自动与手动开关、舵机开/关。
- 回执带原命令 ID、成功/失败及原因；成功仅代表控制器已执行输出，不能宣称机械动作得到传感器验证。
- 重发命令须按 ID 去重；开门命令超时或断线后不得自动重放。网关重启后重新同步状态，不重放旧动作。
- 心跳、Arduino 连接状态与传感器新鲜度分别报告。香橙派在线不等于 Arduino 在线。
- 本地键盘、语音和远程操作统一调用同一套控制逻辑；模式显式上报。手动模式持续到显式恢复自动，仍需与硬件组确认最终规则。
- 电脑或网络断开时，Arduino 继续按已有模式运行；密码键盘和本地自动关门不依赖电脑。远程开门也沿用本地自动关门计时。

1. 去除永久 localOverrides；显示提交中、等待回执、已执行、失败、超时。
2. 将“目标输出状态”和“真实传感器反馈”分开，未接入数据标为未知。
3. 新增湿度、光照明暗、自动/手动模式；隐藏未实现风速、亮度调节与窗户控制。
4. 分别显示视频、识别服务、香橙派、Arduino 连接状态及最近更新时间。
5. 视频持续播放；识别只处理最新待处理帧。人脸验证取新鲜采集帧，不等待或复用旧 YOLO 结果。
6. 取消重复轮询，限制同类请求并发，错误与无数据分别显示。
7. 检查现有 sensor/update 和命令接口的数据结构，新增字段通过明确迁移接入，不能把新协议视为现有接口已支持。

## 实施与验收

1. 先验证电脑摄像头和独立视频预览，记录设备、分辨率、帧率和端到端延迟。
2. 确认 Arduino 板型/引脚，完成最小双向通信：读温湿度、控制灯、收到回执。
3. 接入香橙派网关和 Flask，验证断线、重复命令、过期命令与状态恢复。
4. 更新 GUI 和识别服务，联调语音/键盘/网页的模式一致性。

原 720p/20 FPS 目标不直接套用于这块 ESP32-CAM。先以 640×480 JPEG 流测试，必要时降为 320×240，测量实际 FPS、延迟和稳定性；20 FPS、低于 500ms 仅保留为期望值，未得到硬件验证；连续 30 分钟不出现延迟持续增长，至少两个浏览器同时观看，并比较开启/关闭推理时的效果。这些是目标而非性能承诺。门禁不得显示未经物理反馈证实的“门已打开”。

## 两板代码与历史报告交叉检查

依据：用户先后提供的两份 Arduino 源码，以及《25 组分工及计划书.pdf》第 1–7 页正文和第 9–16 页照片。报告描述的是历史工作，不能作为当前固件已验证的证明；公开文档只保留技术结论，不收录成员学号和个人照片。

### 当前源码的链路

```text
ASRPRO Serial1 TX -> 新 UNO D0/RX（9600 baud）
新 UNO D10 -> 旧 UNO D5（按脉冲数量编码）
新 UNO：雨滴 A0、土壤 A1、触摸 D2、超声波 D8/D9
旧 UNO：温湿度、灯、风扇、键盘、舵机、蜂鸣器、OLED
```

这里 Serial1 属于 ASRPRO，不是 UNO 上的第二个硬件串口。新板使用 Serial，D0 已连接语音模块；不能让网关和语音模块两个发送端未经隔离直接共用该 RX。旧板 D0/D1 用于键盘。双板接 USB 并不意味着现有接线下能直接安全实现双向控制。

### 明确缺口与延迟

- 新板 sendPulses(n) 的显式等待为 30 + 180n + 450 毫秒，之前 blinkStatus(n) 还等待 140×min(n,7)+160 毫秒。关灯 n=6 总计约 2560ms；门铃 n=7 总计约 2880ms。这是发送端函数阻塞时长，不是实测端到端动作耗时。
- 阻塞期间不持续读取串口、触摸和传感器；旧板蜂鸣器也会阻塞脉冲采样。仅优化网页或 Flask 不会消除这些问题。
- 新板仅发送 ID 1–7。旧板支持 ID 8 触摸开门和 ID 9–12 雨水/土壤状态，但本次新板代码没有发送这些 ID，因此不能宣称旧板 OLED 已收到雨水/土壤数据。
- 新板触摸实际发送 ID 7（门铃），不是 ID 8（开门）；应由团队决定产品行为，不擅自改为开门。
- 新板按大于等于 40ms 的接收空闲结束命令，忽略 CR/LF/空格；连续命令可能被拼接。网关协议应明确分帧、长度和错误处理。
- 新板有 Serial.print 传感器与诊断输出，但没有旧板执行回执或状态读取。输出“ASR_CMD”只表示新板解析了指令，不能作为门锁、灯或风扇执行成功依据。
- 雨水/土壤百分比为代码中干湿端点线性映射的相对数值，注释要求校准；不是已校准的物理含水率。超声波 NO_ECHO 应展示未知，不能显示为无人。

### 调整后的网关实施顺序

1. 在不改变接线前记录两板现有功能与烧录版本，确认实际运行是否就是本次两份源码。
2. 优先评估在新板增加独立通信接口承接香橙派；新板未在该代码中占用的引脚不等于实物空闲，具体接口需按接线和资源确认。若采用软件串口，先改阻塞调度并验证与语音收发的兼容性，不直接宣布可行。
3. 将脉冲发送、状态闪灯和蜂鸣器改为非阻塞调度。保留旧脉冲协议仅能作为短期兼容，仍需增加从旧板返回真实控制状态与回执的通道，最终是否替换板间协议待定。
4. 优先验证一个灯光控制命令的完整闭环，再扩展语音、温控与门禁。不把新板发送完成冒充旧板执行完成。
5. 摄像头独立做配置与预览试验，不占用两块 UNO 的控制链路。
